## Решение

Выбран **гибридный подход**: план семестра с вехами ЛР 1–6 фиксируем заранее, а работу над продуктом ведём короткими спринтами по 2 недели.

На практике это выглядит так:

- **Длина спринта:** 2 недели. В каждом спринте — конкретный результат по проекту (например: «собран датасет», «рассчитаны метрики», «построен индекс доступности»).
- **Планирование:** в начале семестра зафиксированы вехи ЛР 1–6 и трудозатраты (~192 ч). В начале и конце каждого спринта — короткая встреча: что делаем, что сделали, что мешает.
- **Встречи:** еженедельный синк команды (понедельник, 30 мин) + показ результатов в конце спринта (пятница, 30–40 мин).
- **Показ результатов:** в конце каждого спринта показываем заказчику и преподавателю то, что получилось: датасет → метрики по районам → индекс доступности → воспроизводимый пайплайн → итоговый отчёт. По итогам каждой ЛР — формальная приёмка.
- **Роли:** менеджер (план-график, встречи), аналитик (требования, метрики, работа с данными), технический организатор (сбор данных, расчёты, воспроизводимость), руководитель рисков (реестр рисков, решения по спорным вопросам).
- **Рабочие документы:** план-график семестра с вехами ЛР + список задач на спринт в GitHub Project. Ведём оба: план — чтобы не потерять сроки, список задач — чтобы видеть текущую работу.
- **Критерии готовности:** общие для всех спринтов — пайплайн запускается одной командой, датасет ≥100 объявлений, ≥10 метрик, индекс по всем районам, два сценария использования (см. устав, разделы 2 и 10).
