# ADR-001: Выбор модели жизненного цикла

Статус: предложено · Дата: 2026-10-10

## Контекст

Проект — аналитический сервис по аренде жилья в Магнитогорске сроком от 1 месяца для приезжих работников заводов (ММК и др.). Команда — 3 человека. Срок жёсткий: один семестр с вехами ЛР 1–6. Бюджет фиксирован — около 144 ч трудозатрат, денежных расходов нет.

Особенности проекта:
- Требования уточняются по ходу: уже меняли объём выборки (1000 → 100 объявлений) и срок аренды (6 мес → 1 мес).
- Нужны регулярные показы результатов заказчику и преподавателю.
- Высокая неопределённость на старте: доступность источников (Циан, Авито), вёрстка объявлений, наличие данных по зарплатам работников ММК.
- Команда маленькая — 3 человека, поэтому роли совмещаются.

## Сравнение подходов

Поставьте 0, 1 или 2 балла по каждому критерию.

| Критерий | Водопад | Scrum | Kanban | Гибрид |
|---|---|---|---|---|
| Требования уточняются по ходу | 0 | 2 | 2 | 2 |
| Нужны регулярные демонстрации | 0 | 2 | 1 | 2 |
| Жёсткий срок и бюджет | 2 | 1 | 1 | 2 |
| Небольшая команда | 1 | 2 | 2 | 2 |
| Много неопределённости на старте | 1 | 2 | 1 | 2 |
| **Итого** | **4** | **9** | **7** | **10** |

## Решение

Выбран **гибридный подход**.

Как это будет выглядеть на практике:
- **Длина спринта:** 2 недели.
- **Планирование:** в начале семестра зафиксированы вехи ЛР 1–6 и трудозатраты (~144 ч). В начале и конце каждого спринта — короткая встреча (что делаем / что сделали / что мешает).
- **Встречи:** еженедельный синк команды (понедельник, 30 мин) + показ результатов в конце спринта (пятница, 30–40 мин).
- **Демонстрация:** в конце каждого спринта показываем заказчику и преподавателю очередной результат — датасет, метрики по районам, индекс доступности, воспроизводимый пайплайн, итоговый отчёт. По итогам каждой ЛР — формальная приёмка.
- **Роли (совмещаются, так как команда 3 человека):**
  - **Менеджер проекта + руководитель рисков** — план-график, встречи, реестр рисков, решения по спорным вопросам.
  - **Аналитик предметной области + работа с данными** — требования, метрики, сбор и очистка объявлений.
  - **Технический организатор + воспроизводимость** — расчёты, пайплайн, запуск одной командой, отчёт.
- **Рабочие документы:** план-график семестра с вехами ЛР + список задач на спринт в GitHub Project. Ведём оба: план — чтобы не потерять сроки, список задач — чтобы видеть текущую работу.
- **Критерии готовности:** общие для всех спринтов — пайплайн запускается одной командой, датасет ≥100 объявлений, ≥10 метрик, индекс по всем районам, два сценария использования (см. устав, разделы 2 и 10).

## Рассмотренные альтернативы

- **Водопад (4 балла)** — не подошёл: требования меняются по ходу, источники данных неопределённы, нужна частая обратная связь от заказчика и преподавателя.
- **Scrum (9 баллов)** — близок по духу, но не учитывает жёсткий фиксированный бюджет и заранее заданные вехи ЛР, которые нужно планировать в начале семестра.
- **Kanban (7 баллов)** — удобен для потока однотипных задач, но слабо поддерживает регулярные демонстрации заказчику и формальную приёмку по ЛР.

## Последствия

- **Что это значит для команды:** все 3 участника работают в одном ритме двухнедельных спринтов; роли совмещаются, поэтому важно следить за загрузкой. Показ результатов в конце спринта — обязательная часть, без него результат не считается принятым. Придётся одновременно вести план-график семестра и список задач спринта — дополнительная нагрузка на менеджера.
- **Что это значит для проекта:** вехи ЛР и трудозатраты (~144 ч) зафиксированы заранее, при этом требования можно уточнять по ходу. Если изменения затрагивают вехи или бюджет — фиксируем новое решение отдельным ADR и обновляем устав.
